2. 需求讨论与问题澄清

grill-with-docs · 问清方案并记录业务概念

user-invoked · 须用户显式调用

在项目目录中讨论计划或设计，需要边讨论边记录业务概念时使用。它内部调用 grilling 逐轮提问，并调用 domain-modeling 澄清术语与关系，已包含这两项工作，无需再依次单独调用。先读已有术语和决定，直接复用已确认结论，只讨论未解决的问题或新出现的冲突；缺少事实时再按需查证。

grilling · 逐轮问清方案与决定

model-invoked · 人或模型可调用

这是 grill-me 与 grill-with-docs 内部使用的提问方法；只需要这套提问方法时也可单独使用。把想法拆成需要决定的问题，记录哪些答案必须先确定；每轮一次提出所有前提已明确的问题，编号并给建议答案。等用户回答后，再讨论依赖这些答案的问题。

3. 调查与方案验证

wayfinder · 理清大型目标的待决问题

user-invoked · 须用户显式调用

目标大而模糊、一个会话讨论不完时使用，范围已经清楚的小功能不需要。先用 grilling 与 domain-modeling 问清最终目标，再在工单系统建立待决问题索引和子工单，记录哪些问题依赖其他答案；按问题需要安排研究、原型、讨论或为作决定而必须完成的准备操作。索引只概括并链接决定，详细依据保留在各工单中。

首次建立索引和问题工单后停止；后续会话先认领一项前提已满足的问题再处理，每会话最多解决一项，研究工单可并行。记录答案、关闭该项，并补充新问题、更新或删除已失效的项；还说不清的问题保留为待澄清范围，超出目标的项关闭并记录理由。默认产出决定，路线明确后交给 to-spec 与 to-tickets；仅当工作确实很小时才直接实施。

它会创建、分派、评论和关闭工单，研究还可能在临时分支提交与推送，需相应配置、工具和授权；研究分支不开 PR。须由人参与的决定通过真实讨论取得，代理不能代答。

/wayfinder 为跨系统迁移建立决策地图，先明确目的地。

prototype · 用简易原型验证设计

model-invoked · 人或模型可调用

设计问题难以只靠讨论决定时，用明确标记为原型的简易程序回答：状态或逻辑是否合理，或界面应该是什么样子。先分清要验证哪一类问题；逻辑原型使用可分享的单文件 HTML，让用户手动推动状态并查看讲解，界面原型提供可切换的不同设计方案。无需为了做原型先运行 research。

原型默认只在内存保存状态，省去正式工程打磨，优先保证容易运行且每次操作后能看见状态变化；确需数据库时用明确标为原型的临时数据。将验证所得决定用于正式实现，原型本身按源流程提交到主分支之外的临时分支，并从实施工单引用问题与结论。换目录开展原型会话时可用 handoff 传递背景和结果；原型是设计证据，不是已验收的生产代码。

diagnosing-bugs · 复现故障并查明原因

model-invoked · 人或模型可调用

遇到疑难故障、偶发失败或性能退化时可直接选此入口，不以先运行 research 或 prototype 为前提。先实际运行一条能检出用户原症状的快速检查，反复执行应能稳定判定，偶发故障则先提高复现率；无法建立检查时，报告尝试和环境限制并停在此处，不凭猜测推断原因。

缩小到仍会失败的最小场景，列出并排序 3—5 个能用实验排除的原因假设，向用户展示后逐项改变变量检验；性能问题先测量正常与异常情况。在能覆盖真实故障的接口处先写失败回归测试，再修复、重跑测试和原始完整场景；没有合适接口时记录限制。结束前清理临时调试内容，说明已验证的原因；命令、日志和捕获材料须脱敏，修复与临时探测按实际授权执行。

/diagnosing-bugs 诊断此间歇失败，先实际运行一条能检出原症状的检查。

codebase-design · 设计代码结构与接口

model-invoked · 人或模型可调用

需要决定模块负责什么、向调用者提供什么接口、接口放在哪里时查阅。模块可以是函数、类或包，包含接口和内部实现；接口是调用者正确使用它所需知道的全部规则，包括参数、必须保持的条件、调用顺序、错误、配置和性能要求。目标是让调用者学习较少规则就能获得完整能力，调用者与测试通过同一接口观察行为。

比较不同设计时，检查复杂逻辑是否集中在模块内部、改动和验证能否集中在一处，以及是否确有不同实现需要替换；需要替换时，调用者仍通过同一接口使用模块。可以假设去掉模块，看看复杂度是消失了还是散落到各调用处，以判断它是否有用；这是思考方法，不是要求删除代码。它是设计参考，不是必须另跑的流程，也不鼓励为假想变化增加抽象。

/codebase-design 比较订单模块两种接口：各负责什么，调用和测试从哪里进入。

4. 规格与实施计划

to-spec · 把已讨论的需求写成规格

user-invoked · 须用户显式调用

需求已经讨论清楚、工作需要跨会话实施时，用它把已有对话与代码理解综合为规格；明确且能在当前会话完成的小任务可直接用 implement，不必为此先写规格和拆任务。规格包含用户问题、方案、用户故事、实现决定、测试决定和范围边界；它沿用已确认结论，不重新做需求访谈。

先与用户确认通过哪些公共接口测试功能，以及这些测试能覆盖什么；优先复用已有、能观察完整行为的接口。工单系统和标签配置齐全后发布规格，并应用 ready-for-agent 标签，发布属于真实写入。它不替代未完成的调查，不承诺自动补齐完整实施蓝图，也不代表用户已确认冻结或授权实施。

/to-spec 把当前讨论整理成规格，先确认通过哪些接口测试功能，再发布。

writing-for-agents · 写清代理要遵循的文档

model-invoked · 人或模型可调用

帮助编写技能、AGENTS.md、CLAUDE.md 以及代理按引用读取的文档，写清触发条件、操作步骤和完成标准，把相关定义与限制放在一起，减少重复和无效说明。

它提供写作参考，不是业务规格或实施计划的生成器；按任务授权修改目标文档，事实仍应来自相应依据。编写技能时还须读取 SKILL-MECHANICS.md，核对元数据与调用方式；一致的过程不保证每次输出逐字相同。

5. 任务拆分

to-tickets · 把规格拆成可验证的小任务

user-invoked · 须用户显式调用

规格或计划较大、需要分批或跨会话实施时，把已有结论拆成能单独展示和验证的小任务，小任务不必再拆。每项都让所需的数据、接口、界面和测试配合完成一项行为，能放进一个新会话，并写明验收条件及必须先完成的任务；若确需先整理代码，先安排这项准备。

大范围机械重构若不能分成独立可用的小功能，先兼容新旧形式，再分批迁移，最后删除旧形式；各批仍不能单独通过检查时，共用集成分支，最后统一集成验证。先让用户确认任务大小、依赖和交付行为，获批准后再发布到配置的工单系统。

本地模式按前置任务优先的顺序，每项写一个文件；远程平台有原生依赖关系时使用它，并默认设置 ready-for-agent 标签，另有指示除外。发布会写文件或创建工单，不关闭或修改父事项，也不要求对这些已可实施的任务再运行 triage。

/to-tickets 将已确认规格拆成能单独展示和验证的小任务，先让我检查哪些任务必须先完成。

6. 实现与测试

implement · 按规格实现一项任务

user-invoked · 须用户显式调用

在当前会话实现一项明确工作，或逐项实现已拆好的任务时使用；与统筹整个规格的 implement-spec 按任务择一，不要求先后连续运行。收到工单引用时，先读取并报告标题，引用有歧义时先澄清；工单访问只在提供引用时必需，已有清楚上下文的小任务也可直接实施。

内部已安排在预先确认的测试接口处尽可能使用 tdd，定期运行类型检查和相关测试，结束时运行完整测试集并调用 code-review。无需仅因页面另列 tdd、code-review 就重复执行同一轮工作；有新改动、检查失败或另有独立复核要求时，再按需要验证。源流程还要求提交当前分支，修改源码、运行检查和 Git 提交均须符合任务授权；实现与审查不等于用户验收。

/implement 实现已确认任务中的行为，通过约定接口验证。

implement-spec · 并行实现规格并集成

user-invoked · 须用户显式调用

规格已拆成带前置依赖的任务，希望统筹整个规格时使用；若要自己逐项推进，则选择 implement。它读取规格和任务关系，从前置任务已完成的项中安排真实子代理并行实施，每项使用新上下文、独立工作树和分支，以集成分支为起点。工单约定、子代理和 Git 工作树工具须可用。

各实施子代理内部使用 tdd，完成前同步集成分支，再由合并代理汇入；有新的可开始任务就继续派工。全部完成后，对集成差异统一运行 code-review 并修正问题，无需再机械地调用另一套实施流程或重复审查。

源流程涉及建分支、改代码、提交、合并、工单流转及清理实施工作树，需要相应授权。若项目通过 PR 关闭工单，或用户要求 PR，在首次合并后创建草稿，完成后标记可审；否则按工单约定结束各任务并报告集成分支。派工或合并完成不等于用户验收。

/implement-spec 按规格中各任务的前置依赖，组织并行实施并合并到同一分支。

tdd · 先写失败测试再实现

model-invoked · 人或模型可调用

只想先用测试验证一个明确行为时可单独使用；implement 已尽可能采用它，implement-spec 的实施子代理也使用它，不必额外重复一轮。写测试前，列出通过哪些公共接口观察行为、能检出什么和遗漏什么，并先与用户确认；测试不直接依赖内部细节。

每轮只做一个接口上的一个行为：先写测试并实际看到失败，再写最少实现使其通过，然后进入下一轮。预期结果来自规格或独立示例，避免照抄实现逻辑来算答案；不能批量写完想象中的测试再统一实现。接口职责有疑问时参考 codebase-design，重构按此版本放到代码审查阶段；测试通过不等于业务验收。

/tdd 通过已确认的公共接口，先为部分退款写一个失败测试。

wizard · 为人工操作生成分步向导

model-invoked · 人或模型可调用

为只有人能完成的操作生成交互式 Bash 向导，例如获取凭据、操作第三方后台或执行一次迁移。先读项目配置，确认人工步骤、要获取的值及其保存位置，再基于源模板编写逐阶段确认的脚本。

生成脚本后做语法与静态检查，交给用户运行，不由代理端到端代跑。向导可能打开网页、写 .env 或 GitHub secrets、执行迁移，须说明实际副作用并保护秘密；默认一次性使用，仅用户要求长期复用时才提交，代理能自行完成的步骤不需此向导。

/wizard 为必须由我完成的 CI secret 配置生成向导。

7. 独立复核

code-review · 分别审查规范与需求

model-invoked · 人或模型可调用

需要审查分支或 PR 时可单独使用。implement 内部已对单项工作安排它，implement-spec 则对整个集成差异统一安排；若没有新改动、失败或额外独立复核要求，不必仅因走到此阶段就重复同一轮审查。先固定用户指定的提交、分支、标签或共同祖先作为比较依据，确认引用有效且差异非空，再查找规格与仓库规范。

安排两个新上下文的真实子代理并行工作，一个检查是否遵守仓库规范，另一个检查是否实现了需求，分别引用具体规则、规格和差异并报告发现数量与各自最严重的问题，避免一方通过掩盖另一方偏差。找不到规格先询问，确认没有后将需求审查标为跳过。它不等于项目另行规定的多角色审查，也不证明问题已修复、测试通过或用户已验收。

/code-review 以 main 为基点，分别审查规范遵循与规格符合度。

04 / SCENARIOS

先选场景，再看交付证据

一个订单取消需求

先沿用已有术语和决定，问清部分取消、退款和库存恢复中尚未明确的规则；小任务可在当前会话实施，跨会话工作再写规格、拆任务。以下是教学提示，不表示任何步骤已发生。

/grill-with-docs 我们要支持部分取消订单，请先查现有领域文档，并区分已知事实与需要我决定的规则。

期待：明确术语、规则与待决事项；需要跨会话实施时，再记录规格和测试决定，拆成含前置依赖、可独立验收的小功能。查看规格副作用与前置条件。

一个间歇性故障

“大概是并发”只是候选假设；先要有能重复触发并检出用户原症状的检查。环境不可达时，报告限制并补证据。

/diagnosing-bugs 保存偶发失败。请先实际运行能检出原症状的检查，记录脱敏输入、执行结果与复现率。

期待：原失败证据、最小复现、被检验的假设、修复后的原场景和相关回归；测试替身只能证明其模型覆盖的范围。

标准正确，需求仍可能错误

先指定比较基点与权威规格，分别检查编码规范和需求实现。没有规格就明确缺失，不能靠规范通过抵消。

/code-review 以 main 为比较基点，规格来源是 docs/specs/order-cancel.md；请分别汇报 Standards 与 Spec。

这里的文件名是教学占位示例，实际使用时替换成真实规格。查看比较基点、规范审查与需求审查步骤。

决定掌握在另一个人手里

知道应该问谁，却不知道答案时，先明确接收人与希望拿回的决定，再写问卷。需要人操作第三方后台时再考虑 wizard。

/to-questionnaire 请帮我为运维负责人准备问卷，我们需要确认上线窗口、回退条件与可用环境。

期待：覆盖知识缺口的 Markdown 问卷；文档生成不表示已发送，也不表示对方已批准。
