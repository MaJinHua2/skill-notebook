02 / WORKFLOW

围绕问题组织工程流程

主线：想法 → 可交付变更

  1. 澄清目标，形成共同语言和必要决策。
  2. 需要运行答案时，用 原型；跨目录以 交接文档往返携带结论。
  3. 跨会话先 综合规格，再 拆可独立验证的小任务与前置依赖；单会话明确工作可直入实施。
  4. 逐票 实施，或让 整个规格集成实现推进前置任务已经完成、现在可以开始的工单（frontier）。
  5. 在事先约定的公共测试接口（seam）上，一次验证一个行为，做 先失败、再通过的测试，再独立 双轴审查；用 PR 正文展示证据，最后 复盘环境。

三条入口与一层设计语言

外部问题堆积：triage 先核实和整理；已经由 to-tickets 生成的可实施票据不再机械 triage。

具体故障：diagnosing-bugs 先实际运行能检出原症状的检查，再讨论能够用实验判断对错的原因假设。

巨大而模糊的工作：wayfinder 先做跨会话决策地图，默认交接给规格与票据流程，不能把决策图直接当实施清单。

domain-modeling 管领域概念；codebase-design 说明怎样用较少接口规则承载完整能力，贯穿主线。

上下文与授权：源主线建议在完成票据拆分前保持讨论连续；容量不足时在阶段边界压缩或交接。/clear、/compact 是源宿主语境，不保证本机支持。发布 Issue、改标签、建分支、提交或推送是源技能的实际操作，只有具体授权与能力齐备后才能执行；本页不会执行它们。

to-tickets · 把规格拆成可验证的小任务

原指南分组：工程 / 规划设计user-invoked · 须用户显式调用
什么时候用
规格或计划较大，需要拆成每项都能独立展示或验证的任务时。
需要什么
计划、规格或当前会话；提供工单引用时须读完整正文与评论，并有工单配置。
会做什么
每票拆成从数据、API、UI到测试都能走通的小功能（tracer-bullet vertical slice）；列清前置任务（blocking edges），由用户确认粒度与依赖后发布。

wayfinder · 理清大型目标的待决问题

原指南分组：工程 / 规划设计user-invoked · 须用户显式调用
什么时候用
目标大而模糊，一个会话讨论不完，需要先找出通往目标的决定时。
需要什么
首次建图提供大型目标、已有约束和工单约定；继续已有地图时提供链接或编号，也可指定要讨论的票据。
会做什么
首次建图：明确目标、建立决策索引与子票，再连接依赖；建图后停止，不在同一会话手动解票。已有地图：认领并解决一个当前可开展的问题（frontier）；每会话最多一票，研究票例外，人的决定不由代理代答。
得到什么
带来源的决定与索引、下一步问题，以及尚不能明确提问和已排除的范围记录。
还需确认
默认产出决定，不是完整功能；会创建、修改、关闭票据，按新决定更新或删除失效票；research 路径可建并推送临时分支但不开 PR。需相关讨论、调研、原型技能和工单工具。
/wayfinder 为跨系统迁移建立决策地图，先明确目的地。

diagnosing-bugs · 复现故障并查明原因

原指南分组：工程 / 实现排障model-invoked · 人或模型可调用
什么时候用
遇到难复现故障、间歇失败或性能退化，需要用证据定位原因时。
需要什么
确切症状、实际环境、脱敏输入与已知正常基线；性能问题须有测量方式。
会做什么
先实际跑出能检出原症状的检查（feedback loop），缩小复现场景；提出 3–5 个可检验假设，逐个观测，再在合适位置补失败测试、修复并回归。
得到什么
失败命令与输出、复现证据、经检验的原因，以及修复后原场景和相关回归结果；没有合适测试位置须明说。
还需确认
环境必须能触达实际故障；无法建立检查时报告并停在该阶段；可写测试、加临时观测与修代码，仍依本次授权，结束须清理临时内容。
/diagnosing-bugs 诊断此间歇失败，先建立能捕捉原症状的反馈环。

research · 查一手资料并写研究笔记

会做什么

需要什么

04 / SCENARIOS

先选场景，再看交付证据

一个订单取消需求

先确认部分取消、退款和库存恢复的业务含义；讨论清楚后再综合规格、拆票与实施。以下是教学提示，不表示任何步骤已发生。

/grill-with-docs 我们要支持部分取消订单，请先查现有领域文档，并区分已知事实与需要我决定的规则。

期待：术语及决定 → 规格中的用户故事与测试决定 → 含前置任务关系、可独立验收的小功能。查看规格副作用与前置条件。

一个间歇性故障

“大概是并发”只是候选假设；先要有能重复触发并检出用户原症状的检查。环境不可达时，报告限制并补证据。

/diagnosing-bugs 保存偶发失败。请先建立针对原症状的反馈环，记录脱敏输入、执行结果与复现率。

期待：原失败证据、最小复现、被检验的假设、修复后的原场景和相关回归；测试替身只能证明其模型覆盖的范围。

标准正确，需求仍可能错误

先指定比较基点与权威规格，分别检查编码规范和需求实现。没有规格就明确缺失，不能靠规范通过抵消。

/code-review 以 main 为比较基点，规格来源是 docs/specs/order-cancel.md；请分别汇报 Standards 与 Spec。

这里的文件名是教学占位示例，实际使用时替换成真实规格。核对固定基点与双轴审查步骤。

决定掌握在另一个人手里

知道应该问谁，却不知道答案时，先明确接收人与希望拿回的决定，再写问卷。需要人操作第三方后台时再考虑 wizard。

/to-questionnaire 请帮我为运维负责人准备问卷，我们需要确认上线窗口、回退条件与可用环境。

期待：覆盖知识缺口的 Markdown 问卷；文档生成不表示已发送，也不表示对方已批准。
