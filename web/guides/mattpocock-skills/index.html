3. 调查与方案验证

research · 查一手资料并写研究笔记

model-invoked · 人或模型可调用

把资料查阅交给拥有新上下文的后台代理，围绕明确问题调查官方文档、源码、规范和第一方接口，逐条追溯到拥有该事实的一手来源。

将结论及各项来源引用保存为仓库中的一份 Markdown 文件，沿用现有研究笔记位置并报告路径。它产出可查证的研究材料，不替代业务决定，也不把资料缺失或尚待核查直接判为缺陷。

diagnosing-bugs · 复现故障并查明原因

model-invoked · 人或模型可调用

针对疑难故障、偶发失败或性能回归，先建立并实际运行能够检出用户原症状的快速反馈环，再复现并缩小场景，提出可证伪假设，逐项改变变量检验原因。无法建立反馈环时，应报告尝试和环境限制，不能直接编造根因。

在能够覆盖真实故障模式的测试接口处先写回归测试，再修复并重跑原场景；没有合适测试接口时如实记录限制。结束前清理临时调试内容，说明根因；命令、日志和捕获材料须先脱敏，修复与临时探测按实际授权执行。

/diagnosing-bugs 诊断此间歇失败，先建立能捕捉原症状的反馈环。

prototype · 用简易原型验证设计

model-invoked · 人或模型可调用

用简易、明确标记为原型的程序回答一个设计问题：状态或逻辑是否合理，或界面应该呈现什么样子。逻辑原型偏向可分享的单文件 HTML，界面原型提供可切换的不同设计变体。

原型默认仅在内存保存状态，省去生产级打磨，优先保证容易运行并能看见状态变化。验证所得决定可用于正式实现，原型本身按源流程提交到独立 prototype 分支并从实现事项引用；它是设计证据，不是已验收的生产代码。

/prototype 做一个可手动推动状态的原型，比较部分取消行为。

wayfinder · 理清大型目标的待决问题

user-invoked · 须用户显式调用

面向大到无法在一个会话内说清的模糊目标，在工单系统建立决定地图，把研究、原型、访谈和决策前置任务组织为带依赖的子事项，逐步澄清通往目标的路径。地图只索引决定，具体依据保留在对应事项中。

默认成果是明确的决定，而非直接实现目标；尚不能准确提问的部分继续保留为待澄清范围，不硬拆成执行任务。它会创建、分派、评论和关闭工单，研究分支也可能提交与推送，需按实际授权执行；有人参与的决定不能由代理代答。

/wayfinder 为跨系统迁移建立决策地图，先明确目的地。

codebase-design · 设计代码结构与接口

model-invoked · 人或模型可调用

提供设计深模块的共同词汇：用较小接口承载较多行为，把可替换实现放在恰当的 seam，让调用方与测试通过同一接口观察行为。接口还包括不变量、调用顺序、错误、配置及性能要求。

用于推敲模块形状、接口和测试位置，关注复杂度是否真正集中、修改是否局部，以及实现是否确实需要替换。它是设计参考，不是自动生成实施蓝图的流程，也不鼓励为假想变化增加抽象。

/codebase-design 比较订单模块两种接口的深度与测试接缝。

user-invoked · 须用户显式调用

4. 规格与实施计划

5. 任务拆分

to-tickets · 把规格拆成可验证的小任务

user-invoked · 须用户显式调用

把规格、计划或已讨论内容拆成可独立展示和验证的端到端小任务，每项写明验收条件及真正阻塞它的前置任务。普通功能纵向贯穿所需层次；无法单独保持可用的大范围机械重构采用扩展、分批迁移、收缩的依赖序列。

6. 实现与测试

implement · 按规格实现一项任务

user-invoked · 须用户显式调用

根据已有规格或票据实现一项明确工作；收到票据引用时，先读取并确认标题，引用有歧义时先澄清。在已约定的测试接口处尽可能使用 tdd，过程中运行类型检查和相关测试，结束时运行完整测试集并调用 code-review。

源流程还要求将工作提交到当前分支，因此会修改源码、运行检查并产生 Git 提交，须核对任务授权与项目约定。实现与审查结果需要实际证据，不能把执行完技能等同于用户验收。

implement-spec · 并行实现规格并集成

user-invoked · 须用户显式调用

读取规格及已拆好的带依赖票据，将它们作为任务图处理，在可执行任务中安排真实实施子代理并行工作。各任务使用独立工作树和分支，实施前基于集成分支，完成后由合并代理集成到同一分支。

tdd · 先写失败测试再实现

model-invoked · 人或模型可调用

通过事先与用户确认的公共测试接口验证可观察行为，每次只完成一个行为的失败测试与最小实现，再开始下一个循环。测试保持对内部重构不敏感，避免复制实现逻辑的自证断言。

它会编写并运行测试、修改实现，必须先看到失败再追求通过，不能先批量写完想象中的测试后统一实现。模块接口本身有疑问时参考 codebase-design；重构按源流程放到复核阶段，不把测试通过写成业务验收通过。

/tdd 在已确认的公共接缝上，先为部分退款写一个失败测试。

wizard · 为人工操作生成分步向导

model-invoked · 人或模型可调用

为只有人能完成的操作生成交互式 Bash 向导，例如获取凭据、操作第三方后台或执行一次迁移。先读项目配置，确认人工步骤、要获取的值及其保存位置，再基于源模板编写逐阶段确认的脚本。

生成脚本后做语法与静态检查，交给用户运行，不由代理端到端代跑。向导可能打开网页、写 .env 或 GitHub secrets、执行迁移，须说明实际副作用并保护秘密；默认一次性使用，仅用户要求长期复用时才提交，代理能自行完成的步骤不需此向导。

/wizard 为必须由我完成的 CI secret 配置生成向导。

7. 独立复核

code-review · 分别审查规范与需求

model-invoked · 人或模型可调用

以用户指定的提交、分支、标签或合并基点固定比较范围，核对有效引用、差异与规格来源，分别由真实并行子代理审查仓库规范和需求符合度。两条审查轴独立报告，避免规范通过掩盖需求偏差。

审查须引用具体规则、规格与差异证据；找不到规格时先询问，确认没有规格后将需求审查标为跳过。结果是并列的审查结论与问题，不是已经修复、测试通过或用户验收的证明。

/code-review 以 main 为基点，分别审查规范遵循与规格符合度。

pr · 编写合并请求说明

model-invoked · 人或模型可调用

编写 PR 正文，用最小的图、差异草图或结构视图说明变化，附前后对比的截图、输出或测试证据，让审阅者看清行为与影响。文字沿用项目领域语言，保持简短。

正文还说明变更是否容易撤回，以及合并的影响范围与风险。它提供说明模板，不负责证明未执行的测试，也不因正文生成就表示 PR 已创建、合并或获得验收。

/pr 根据现有差异和前后证据拟写 PR 正文。

本指南将它放在验收后作为可选的代理工作环境复盘：读取指定会话的一手记录，查找导航、自动检查、编码规范、代理指引、工具使用和信息获取方面的改善候选。

04 / SCENARIOS

先选场景，再看交付证据

一个订单取消需求

先确认部分取消、退款和库存恢复的业务含义；讨论清楚后再综合规格、拆票与实施。以下是教学提示，不表示任何步骤已发生。

/grill-with-docs 我们要支持部分取消订单，请先查现有领域文档，并区分已知事实与需要我决定的规则。

期待：术语及决定 → 规格中的用户故事与测试决定 → 含前置任务关系、可独立验收的小功能。查看规格副作用与前置条件。

一个间歇性故障

“大概是并发”只是候选假设；先要有能重复触发并检出用户原症状的检查。环境不可达时，报告限制并补证据。

/diagnosing-bugs 保存偶发失败。请先建立针对原症状的反馈环，记录脱敏输入、执行结果与复现率。

期待：原失败证据、最小复现、被检验的假设、修复后的原场景和相关回归；测试替身只能证明其模型覆盖的范围。

标准正确，需求仍可能错误

先指定比较基点与权威规格，分别检查编码规范和需求实现。没有规格就明确缺失，不能靠规范通过抵消。

/code-review 以 main 为比较基点，规格来源是 docs/specs/order-cancel.md；请分别汇报 Standards 与 Spec。

这里的文件名是教学占位示例，实际使用时替换成真实规格。核对固定基点与双轴审查步骤。

决定掌握在另一个人手里

知道应该问谁，却不知道答案时，先明确接收人与希望拿回的决定，再写问卷。需要人操作第三方后台时再考虑 wizard。

/to-questionnaire 请帮我为运维负责人准备问卷，我们需要确认上线窗口、回退条件与可用环境。

期待：覆盖知识缺口的 Markdown 问卷；文档生成不表示已发送，也不表示对方已批准。
