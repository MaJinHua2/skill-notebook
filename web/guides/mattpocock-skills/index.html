01 / GET STARTED

从当前问题入手

技能是一份工作方法

每个 SKILL.md 描述何时用、做什么、产出什么；它可能组合其他技能、工具或子代理。读懂文字、宿主发现技能、真实执行成功是三件事。

拿不准入口时，先看 ask-matt。有仓库的需求访谈看 grill-with-docs；无目录的想法讨论看 grill-me。

两种调用策略

user-invoked 必须由用户显式调用。源 Claude 配置使用 disable-model-invocation: true，Codex 对应 policy.allow_implicit_invocation: false。

model-invoked 允许人或模型调用：既可主动要求，也可由模型按触发语义选用；并非仅供内部调用。

示例语法：本页用源文档中的 /skill-name 表达调用，再附中文任务作为教学示例。各宿主的命令入口、命名空间、隐式触发与工具权限有差异；这里不声称当前机器已加载所有技能。复制示例只写剪贴板。

安装说明只作来源引用

先确认自己的宿主、版本和安装渠道。以下是源 README 中的 Codex 安装示例，未经本页执行或本机兼容性验证，不能保证安装成功。源 README 说明每个宿主选择插件或可编辑文件一种方式，避免重复安装；其更新行为也是来源描述。

codex plugin marketplace add mattpocock/skills

核对其他宿主、安装方式与更新说明

工程流程前，源文要求用 setup-matt-pocock-skills 配置 tracker、triage 标签与领域文档。配置会产生真实写入，按具体任务授权使用。

02 / WORKFLOW

围绕问题组织工程流程

主线：想法 → 可交付变更

  1. 澄清目标，形成共同语言和必要决策。
  2. 需要运行答案时，用 原型；跨目录以 交接文档往返携带结论。
  3. 跨会话先 综合规格，再 拆纵向票据与依赖；单会话明确工作可直入实施。
  4. 逐票 实施，或让 整个规格集成实现推进就绪 frontier。
  5. 在约定接缝逐片做 红绿测试，再独立 双轴审查；用 PR 正文展示证据，最后 复盘环境。

三条入口与一层设计语言

外部问题堆积：triage 先核实和整理；已经由 to-tickets 生成的可实施票据不再机械 triage。

具体故障：diagnosing-bugs 先获得能捕捉原症状的反馈环，再讨论可证伪假设。

巨大而模糊的工作：wayfinder 先做跨会话决策地图，默认交接给规格与票据流程，不能把决策图直接当实施清单。

domain-modeling 管领域概念；codebase-design 管深模块设计词汇，贯穿主线。

上下文与授权：源主线建议在完成票据拆分前保持讨论连续；容量不足时在阶段边界压缩或交接。/clear、/compact 是源宿主语境，不保证本机支持。发布 Issue、改标签、建分支、提交或推送是源技能的实际操作，只有具体授权与能力齐备后才能执行；本页不会执行它们。

diagnosing-bugs

工程 / 实现排障model-invoked · 人或模型可调用
用途
对难复现故障或性能回归建立证据驱动诊断闭环。

/diagnosing-bugs 诊断此间歇失败，先建立能捕捉原症状的反馈环。

04 / SCENARIOS

先选场景，再看交付证据

一个订单取消需求

先确认部分取消、退款和库存恢复的业务含义；讨论清楚后再综合规格、拆票与实施。以下是教学提示，不表示任何步骤已发生。

/grill-with-docs 我们要支持部分取消订单，请先查现有领域文档，并区分已知事实与需要我决定的规则。

期待：术语及决定 → 规格中的用户故事与测试决定 → 含阻塞依赖的可验收切片。查看规格副作用与前置条件。

一个间歇性故障

“大概是并发”只是候选假设；先要能重复触发用户原症状的反馈环。环境不可达时，报告限制并补证据。

/diagnosing-bugs 保存偶发失败。请先建立针对原症状的反馈环，记录脱敏输入、执行结果与复现率。

期待：原失败证据、最小复现、被检验的假设、修复后的原场景和相关回归；测试替身只能证明其模型覆盖的范围。

标准正确，需求仍可能错误

先指定比较基点与权威规格，分别检查编码规范和需求实现。没有规格就明确缺失，不能靠规范通过抵消。

/code-review 以 main 为比较基点，规格来源是 docs/specs/order-cancel.md；请分别汇报 Standards 与 Spec。

这里的文件名是教学占位示例，实际使用时替换成真实规格。核对固定基点与双轴审查步骤。

决定掌握在另一个人手里

知道应该问谁，却不知道答案时，先明确接收人与希望拿回的决定，再写问卷。需要人操作第三方后台时再考虑 wizard。

/to-questionnaire 请帮我为运维负责人准备问卷，我们需要确认上线窗口、回退条件与可用环境。

期待：覆盖知识缺口的 Markdown 问卷；文档生成不表示已发送，也不表示对方已批准。
