从需求到 Git
多智能体生产链路

以智能体主导、人类辅助的方式组织软件开发。每个工程环节配一个协作技能和一个文档或证据技能，让需求、设计、实现、审核与验收可以沿同一依据衔接。

先共同理解，再分工执行参与者读取同一版权威需求，形成清晰交接。业务事实、关键取舍和需要额外授权的操作由人参与；其余工作在已授权范围内自主推进。

THE OPERATING MODEL

这条链路怎样运转

智能体主导工作

主代理负责组织。需求分析、实施、代码与质量审核、风险核实和需求验收分别承担任务；审核发现交实施者处理，再按影响范围复核。

人类提供必要判断

先查资料并形成可审阅结果。只有需要业务事实、产品取舍或额外授权时才请人参与；已确认决定和授权内常规事项继续推进。

共同需求来源：各角色开始、接手和交接前，读取同一权威需求正文的对应版本或内容指纹，并说明本角色范围。用户变更即时生效；受影响的旧任务先停止，按授权同步正文并通知相关角色。

开发验证

新功能或缺陷修复

在适用任务中先确认目标测试有效失败，再做最小实现并复测。

参与角色实施者、主代理交接产物代码、测试与 RED / GREEN 证据

开发验证

02 / PEOPLE & AGENTS

七角色分工

角色提供职责边界；是否派工、采用哪些角色以及授权范围以当前任务和 Codex 可用能力为准。

项目经理 / 主代理

统筹需求版本、任务分派、证据、问题整合和交接。

需求分析者

澄清目标、保持项和验收条件，维护权威需求正文。

实施者

完成范围内设计、实现、配套材料和自检。

代码质量审核者

只读检查实现必要性、可维护性和测试证据。

代码评审者

只读核对正确性、兼容性、边界和副作用。

风险审核者

核实、去重和分级已有发现，说明证据与范围。

需求验收者

依据确认需求独立验收，并报告结论与证据层级。

03 / DELIVERABLES

每次交接需要什么

下列内容可以复用既有 Issue、专题或文档的相应部分；同一事实只保留一个权威来源。

需求正文

目标、边界、保持项、已确认来源、验收条件，以及版本或内容指纹。

设计与决策

固定基线、模块与接口、数据关系、失败路径、可选方案和实际决策。

计划与测试方案

责任分工、依赖、执行范围、代表输入、预期、验证方法和交接条件。

实施与回归证据

实际差异、工具与命令、测试结果、受影响消费者和未验证项。

审核与验收记录

位置、触发条件、影响、事实与风险；逐项记录通过、失败、受阻或未验证。

Git 提交说明

真实关联、变更原因、范围、兼容边界和验证结果；遵守项目格式。

05 / PRACTICAL BOUNDARIES

使用时的关键适配

这些说明对应当前讨论和 Cyto 项目约定，实际任务仍应核对所用仓库、工具和授权。

多角色讨论与真实派工

dev-team 的原生流程是 PM、架构、开发、QA 四个只读视角并行发言，由主代理综合；它不保证角色之间直接辩论。现有七角色需要通过实际可用的 Codex 派工能力适配，不能声称自动映射。

设计、决策与计划

product-capability 提供能力合约和设计输入；具体模块设计仍须补齐。重大决策记录真实取舍；没有新决定时复用既有依据。blueprint 适合多会话或多 PR，较小任务使用精简计划。

测试驱动与等价重构

tdd-workflow 原文要求 RED/GREEN、覆盖率目标和检查点提交；项目授权与实际测试入口优先。保持行为的重构先建立通过的旧基线，不为流程制造修前失败。

审核和验收各自独立

安全技能提供检查清单，报告由审核者依据实际发现形成。测试全绿或构建通过不能代替需求、真实设备、样本或客户验收；未验证项要明确列出。

项目工具与文档

Cyto 采用 C++11、Qt 5 和 qmake；不要照搬 C++17/20、CMake、npm 等示例。复用项目已有文档和测试入口，先区分生成区域与手写材料。

提交与专业扩展

Cyto 提交格式采用 type[模块]: 中文主题 [#真实编号]，正文填写真实关联。mle-workflow 用于机器学习任务，council 用于存在实际取舍的多立场讨论。
